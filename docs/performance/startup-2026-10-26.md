# Profilage du démarrage de LazyVPN

## Résultat

Sur cette machine, à cache de serveurs valide, le chemin critique est graphique.
Les profils sont prêts dans le moteur avant que la fenêtre soit affichée.
Un second problème indépendant apparaît lorsque le cache est ancien : le
rafraîchissement réseau est attendu avant de publier les profils déjà disponibles.

Les mesures portent sur `20b1bc9` avec des sondes temporaires identiques en debug
et release. Les sondes ont ensuite été retirées, et un binaire release propre a
été recompilé. Ces mesures précèdent le correctif décrit dans la validation ci-dessous.

## Méthode et périmètre

- Linux, Niri/Wayland ; GPU détecté : AMD Radeon Graphics, RADV REMBRANDT,
  Mesa 26.2.4-arch3.1. Les bibliothèques NVIDIA sont aussi installées.
- GPUI Kit 0.6.6 ; crates GPUI 0.3.6.
- Configuration normale : ProtonVPN, cache de 733 serveurs, deux profils locaux,
  aucun tunnel WireGuard actif lors des essais. Le cache normal était valide.
- Délai visible : depuis le lancement du processus jusqu'à l'apparition de sa
  fenêtre dans les fenêtres Niri, avec interrogation toutes les 10 ms environ.
  Ce n'est pas une mesure de la fin de l'animation du compositeur.
- Sondes `Instant` sur le chemin principal et le moteur, sans données de
  connexion ni secrets. L'événement `view.ready` signifie que la vue a reçu ses
  données, pas que tous les pixels et toutes les images ont été présentés.
- Échantillonnage CPU avec `gprofng collect app -p hi`, puis rapports de fonctions
  exclusives/inclusives. Les temps sous échantillonneur ne sont pas utilisés
  comme latences normales : son surcoût est important.
- Petits échantillons de trois démarrages par variante, sur une session desktop
  active. Pas de purge globale des caches, pas de percentile revendiqué.

## Mesures normales, même source

Essais alternant les deux modes de compilation :

- Debug, fenêtre visible : **1 886,8 / 1 105,7 / 1 090,1 ms**.
  Médiane : **1 105,7 ms**.
- Release, fenêtre visible : **473,2 / 453,1 / 462,3 ms**.
  Médiane : **462,3 ms**, soit environ **2,4 fois plus rapide**.
- Release, publication des profils par le moteur : **33,309 / 31,057 / 29,043 ms**
  depuis l'entrée dans `main`.
- Lecture et application de la palette release : **0,044 / 0,046 / 0,036 ms**.
- Appel `open_window` release : **351,672 / 348,690 / 361,478 ms**.
  Cela inclut la création de la fenêtre native, du renderer et le premier rendu.

Le binaire installé, antérieur à cette branche, a aussi été mesuré en preview :
709,5 / 456,8 / 450,7 ms. Il sert de contrôle, pas à isoler le seul effet du mode
de compilation, puisque sa version de code diffère.

Le premier lancement du nouveau release juste après compilation a pris
2 870,4 ms, dont environ 1 865 ms dans la construction de l'application GPUI.
Cette observation isolée ne permet pas de conclure sur un coût à froid stable ;
elle montre que les résultats à chaud ne couvrent pas tous les cas perceptibles.

## Décomposition du moteur

Dans les trois essais release alternés :

- Création du gestionnaire de credentials : 6,4–8,6 ms.
- Chargement des credentials du fournisseur : 12,5–14,1 ms.
- Lecture du cache de serveurs : 1,4–1,7 ms.
- Détection VPN : 0,16–0,36 ms dans le cas sans tunnel.
- Nettoyage de l'état orphelin : 2,2–2,9 ms.
- Construction de la liste finale : 0,9–1,2 ms.

Ces durées s'exécutent en parallèle de l'initialisation graphique : les enlever
ne supprimerait pas autant de temps à l'ouverture de la fenêtre.

## Expérience : cache ancien et réseau indisponible

Une copie isolée de la configuration et du cache a reçu des dates anciennes.
Les requêtes HTTP ont été dirigées vers un proxy local inaccessible pour obtenir
des échecs immédiats, sans modifier le cache normal.

- Fenêtre visible : **675,5 ms**.
- Rafraîchissement des serveurs : **6 036,7 ms**.
- Profils publiés par le moteur : **6 080,2 ms**.
- Profils reçus par la vue : **6 214,7 ms**.

La cause est l'attente de `fetch(...).await` dans `get_servers`, y compris dans
la branche de cache ancien dont le commentaire dit « background ». Les trois
tentatives sont séparées par des pauses de 2 et 4 secondes. Des erreurs réseau
qui attendent un timeout peuvent durer davantage ; le délai de 30 secondes ne
couvre actuellement que l'obtention de la réponse, pas toute la lecture JSON.

Points d'entrée : `src/app.rs` (`initialize`, `refresh_servers`),
`src/utils/gluetun.rs` (`get_servers`, `ServerFetcher::fetch`, `fetch_provider`),
`src/gui/engine.rs` (`run_owned`, première publication du snapshot).

**Optimisation recommandée en premier :** publier immédiatement un cache
utilisable, signaler sa fraîcheur, puis rafraîchir en tâche de fond. Conserver
les profils locaux, dédupliquer les rafraîchissements et borner l'opération HTTP
complète. Une liste de serveurs cachée ne doit pas être présentée comme une
preuve que le tunnel est opérationnel.

## Expériences : polices et découverte graphique

Le système expose **2 587 fichiers de polices**. Les échantillons CPU montrent
notamment `FontSystem::get_font_matches` / `FontMatchKey::new`, ainsi que
`WgpuContext::instance`, l'énumération Vulkan et des bibliothèques NVIDIA/EGL.

Deux contraintes ont été appliquées uniquement aux processus de test :

1. Catalogue Fontconfig de six fichiers, conservant notamment JetBrainsMono
   Nerd Font, des variantes et des polices de repli.
2. Pilote Vulkan RADV et fournisseur EGL Mesa exclusivement.

Mesures exploratoires séparées, en release :

- Pilotes restreints : 396,6 / 415,6 / 414,3 ms.
- Polices restreintes : 476,2 / 359,6 / 342,8 ms.
- Les deux : 136,9 / 150,4 / 211,1 ms.

Une seconde série alternée confirme la direction :

- Configuration normale : **673,8 / 648,3 / 458,9 ms**.
- Configuration graphique restreinte : **204,3 / 134,9 / 139,0 ms**.

Ces essais démontrent un potentiel, pas un patch distribuable : il ne faut pas
retirer les polices de l'utilisateur ni imposer AMD à toutes les machines.
La solution durable doit préserver les glyphes, les replis et les systèmes
multi-GPU. Examiner une sélection/initialisation moins avide des polices et un
parcours GPU qui évite le chargement de backends inutiles, avec repli explicite.
Ces changements touchent surtout GPUI, plutôt que la logique VPN.

## Autres pistes, moins prioritaires

- **Drapeaux :** `src/gui/view.rs` affiche les SVG en 16 × 12, mais
  `ImageAssetLoader` appelle `render_single_frame(..., 1.0)` ; les fichiers ont
  généralement un viewBox de 640 × 480. Le profil CPU retrouve la rasterisation
  et la conversion de pixels, particulièrement coûteuses en debug. Tester une
  rasterisation à la taille utile avec prise en compte du DPI, ou des bitmaps
  précalculés. Aucun gain de latence attribuable aux seuls drapeaux n'a été
  mesuré dans cette investigation.
- **Pipelines GPU :** GPUI crée ses pipelines au démarrage avec `cache: None`.
  Un cache explicite/précompilation mérite un essai, mais l'énumération des
  drivers et les polices ressortent davantage ici. Le driver peut déjà avoir
  son propre cache : ne pas assimiler `cache: None` à l'absence de tout cache.
- **Credentials :** le test de disponibilité, `exists` puis `retrieve` répètent
  des accès au keyring. Réduire ces lectures serait utile, mais le moteur est
  déjà prêt bien avant l'affichage dans le cas normal.
- **Palette :** ne pas ajouter de cache supplémentaire. Le fichier généré est
  déjà local et sa lecture/application représente quelques centièmes de ms.

## Suite proposée

1. Tester les performances avec le binaire release, pas le binaire debug.
2. Corriger le chemin cache d'abord / rafraîchissement asynchrone, avec un test
   réseau indisponible et un test de cache incomplet.
3. Faire une expérimentation GPUI ciblée sur polices et backends graphiques,
   vérifiée sur plusieurs configurations et DPI.
4. Mesurer séparément le rendu des drapeaux avant de modifier leurs assets.

## Validation du correctif cache-first

Le GUI publie désormais les profils sauvegardés avant le rafraîchissement réseau.
Les tests couvrent les caches ancien, frais, incomplet, absent et corrompu, les
profils locaux, la déduplication, l'annulation et une réponse HTTP dont le corps
reste bloqué. Les suites avec et sans fonctionnalités par défaut passent ; les
quatre tests réseau privilégiés déjà ignorés le restent.

Dans la fenêtre native, avec 733 profils et un proxy inaccessible, la capture
montre la liste et le bouton Connect actif pendant le rafraîchissement. La
fermeture annule celui-ci en 56,3 ms. Le premier lancement après compilation
ouvre la fenêtre en 3 279,8 ms ; trois répétitions à chaud, avec cache à nouveau
vieilli avant chaque lancement, donnent 527,5 / 452,0 / 449,0 ms. Ces dernières
mesurent l'apparition de la fenêtre, pas un nouvel événement instrumenté de
réception des profils. L'attente réseau est supprimée du chemin de publication ;
le coût graphique à froid reste à traiter.

Le binaire release de test est reconstruit, sans remplacement du binaire installé.

## Rendu des drapeaux et limites de l'API GPUI

Le chargeur de drapeaux utilise maintenant l'API `Asset` de GPUI pour rasteriser
les SVG à 16 × 12 pixels logiques, multipliés par l'échelle de la fenêtre.
La clé du cache contient la taille physique : changer de DPI recharge une image
adaptée, sans modifier les fichiers SVG ni les polices de l'utilisateur.
Les 271 SVG passent un test de dimensions à 100 %, 150 % et 200 %. Le rendu
natif en preview a été inspecté ; les tests GUI passent.

Comparaison release alternée en preview, cinq lancements par binaire :

- Avant : 2 036,7 / 459,0 / 448,1 / 441,2 / 450,4 ms.
- Après : 447,8 / 457,1 / 441,5 / 465,1 / 475,6 ms.

Le premier lancement de l'ancien binaire est atypique. Les quatre paires
suivantes ne montrent aucun gain net sur l'apparition de la fenêtre. Ce changement
réduit la taille des images rasterisées ; il ne résout pas le coût d'initialisation
graphique. Les mesures sont dans `/tmp/opencode/lazyvpn-flags-ab.json`.

Les sources publiées `gpui-pre-wgpu` 0.3.6 et 0.3.10 ont été examinées : le
constructeur Linux charge toujours les polices système et l'instance WGPU active
Vulkan et GL. L'API de lancement utilisée ne propose pas d'injection de catalogue
de polices ni de sélection des backends. Les gains principaux demandent donc une
modification de la dépendance GPUI ; une simple mise à jour de version ne fournit
pas ces réglages. Aucun pilote ni catalogue système n'a été restreint dans le code
de LazyVPN.

## Artefacts locaux

Les artefacts bruts sont sous `/tmp/opencode/` :

- `lazyvpn-profile.py` : harnais Niri, démarrage, attente des sondes, fermeture.
- `lazyvpn-startup-instrumentation.patch` : sondes temporaires, applicables au
  commit étudié ; elles ne sont plus présentes dans les sources.
- `lazyvpn-same-code-ab.json` : comparaison debug/release et phases détaillées.
- `lazyvpn-graphics-ab.json` : essai alterné des contraintes graphiques.
- `lazyvpn-stale-offline.json` : scénario de cache ancien hors ligne.
- `lazyvpn-cpu-release-functions.txt` et `lazyvpn-cpu-all.txt` : rapports CPU.
- `lazyvpn-normal-release.json` : premier lancement après build et répétitions.

Le binaire release propre est disponible dans le répertoire `target/release`
du dépôt principal. Le binaire installé dans `/usr/bin` n'a pas été remplacé.
